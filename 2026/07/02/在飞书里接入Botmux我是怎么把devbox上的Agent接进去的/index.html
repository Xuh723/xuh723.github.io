    在飞书里接入 Botmux，我是怎么把 devbox 上的 Agent 接进去的

    概述

    这两天主要在折腾一件事：把开发机上的 Agent 真正接到飞书里。这样人不在电脑前的时候，也能继续接管远端会话，手机上也能直接盯远端任务的状态。

    一开始我的目标其实很朴素，就是先在 devbox 上把 tmux 装顺，让 Agent 进程能稳定常驻，然后再想办法把这个会话桥到飞书里。中间也看了不少现成教程，大多数都是开箱即用的“一把梭”配置，但我这次更想自己一步步配清楚，顺便弄明白这套东西到底是怎么串起来的。

    后来把终端换成了 Ghostty，装好了 tmux，又去翻了几个能把飞书和终端桥接起来的项目。本来只是想找个现成方案参考一下，结果顺手看了几圈，最后还是选了 botmux。原因也很直接：它不是重新造一套 Agent 平台，而是直接桥接现有 CLI 进程，这个思路我很喜欢。

    最后实际跑通的结果也不错：我在开发机上装了 botmux，又接了 Claude Code 和 TraeX 两个终端，创建了两个飞书机器人。现在已经能直接在飞书里跟 Agent 对话，也能拉个群让两个 Agent 互相讨论。这个场景我之前就一直想试，这次算是真正打通了。

    这篇文章主要记三件事：

    • 我到底想解决什么问题
    • 为什么 tmux 是这套方案的前提
    • botmux 适合放在整条链路里的哪个位置

    我想解决的到底是什么问题

    如果只是本地终端里跑 Agent，其实体验已经够好了。

    但一旦 Agent 真正开始帮你干活，就会出现几个很现实的问题：

    • Agent 在开发机里跑着，但飞书收不到它的上下文
    • 手机上只能看消息，没法继续接管会话
    • 终端、飞书、网页是三套入口，状态割裂
    • 想让两个不同的 Agent 一起讨论时，操作非常别扭

    简单来说，问题不是“我能不能启动一个 Agent”，而是“我能不能把一个已经跑起来、而且最好常驻的 Agent，会话级地暴露到飞书里”。

    这个问题用普通 Bot 思路不太好解，因为大多数聊天机器人只能做到“发消息”，做不到“接管一个还活着的终端会话”。

    为什么先装 tmux

    这一步我现在回头看，基本是整套方案的前提。

    Botmux 本身虽然负责把飞书、网页和终端桥起来，但底层如果没有一个稳定常驻的终端会话，很多体验都站不住。尤其是在开发机环境里，网络断一下、SSH 退一下、笔记本一合上，进程就没了，那飞书端再强也没有意义。

    tmux 解决的是这个问题：

    • 让 CLI 会话常驻
    • SSH 断了，底层 Agent 还活着
    • 之后不管是本地 attach，还是从飞书 adopt，本质上都是在接同一个会话

    所以我今天虽然表面上是在“研究怎么远程控制 Agent”，但实际上第一件正事还是把 tmux 装明白。

    顺手一提，我中途也换了 Ghostty。不完全是因为必须，只是既然都在整理终端工作流了，就顺便把本地终端环境也换成一个我更愿意长期用的。

    为什么最后选了 Botmux

    我一开始并没有直接认定就是它。

    本来只是想找一个现成方案参考一下，尤其是看看有没有别人已经把“飞书 + 远端终端 + Agent”这条链路串起来了。后来翻了一圈，发现 botmux 的思路比较对我胃口。

    它最打动我的点不是“功能很多”，而是这件事：

    它不是做一个 SDK wrapper，而是直接桥接已有 CLI 进程。

    这个设计选择很关键。

    因为如果你平时已经在用 Claude Code、Codex、TraeX 这类 CLI，那么你真正舍不得丢的，其实不是某个聊天窗口，而是整套 CLI 运行时本身：

    • 已经登录好的环境
    • 已经配好的工具链
    • 已经有的 memory、hooks、MCP
    • 已经习惯的终端工作方式
    • 已经跑起来的 tmux 常驻会话

    Botmux 的做法，相当于不是把这些东西重做一遍，而是把它们直接暴露到飞书和 Web 端。

    这就很像“远程接管同一个终端”，而不是“在飞书里再开一个缩水版聊天副本”。

    Botmux 到底做了什么

    按我这次实际理解，它做的事大概可以概括成一句话：

    把飞书会话、Web 终端和开发机上的 CLI 进程桥接到一起。

    这件事拆开来看，有几个很实用的能力。

    飞书、Web、tmux 共用一个会话

    这是我最看重的能力。

    一旦底层进程挂在 tmux 里，botmux 再把这个会话映射到飞书，体验就完全不一样了：

    • 电脑上可以继续在终端里操作
    • 手机上可以直接在飞书里继续发命令
    • 网页端也能接管
    • 三边不是各聊各的，而是在共享一个上下文

    这个和普通聊天机器人最大的区别就在这里。

    会话接管

    botmux 文档里有 /adopt 这类命令，本质上就是在说：如果底层 CLI 已经在跑，飞书这边可以接管它。

    这就很适合我这种场景：

    • 在电脑前把事情开个头
    • 人离开工位
    • 后面拿手机进飞书继续盯进度或补几句命令

    多机器人协作

    这个是我今天最兴奋的一点。

    我最后接了两个终端：

    • 一个走 Claude Code
    • 一个走 TraeX

    然后各自挂成飞书机器人。这样拉个群之后，就不是“一个人对一个 Bot”了，而是可以真的让两个 Agent 在同一个群里协作，甚至互相讨论。

    之前我就一直想试这种玩法，今天终于跑通。

    它的意义不只是好玩，而是很像把不同能力的 Agent 变成一个真正可协作的工程环境：

    • 一个负责实现
    • 一个负责 review
    • 一个负责查资料
    • 或者一个偏外部工具，一个偏代码理解

    这比单 Agent 聊到底灵活很多。

    Oncall 和持续上下文

    这个虽然我今天还没完全展开用，但 botmux 的设计很明显就是冲着这种场景去的。

    它不是只适合临时聊天，而是很适合下面这些东西：

    • 报警群
    • 值班群
    • 项目群
    • 定时巡检
    • 周期性播报

    因为它底层依赖的是常驻会话，而不是“一次对话一次新开”，所以会更适合那种上下文要持续积累的工作流。

    接入前我觉得最需要想清楚的几件事

    这部分比安装命令本身更重要。

    1. 先决定 Agent 跑在哪里

    我自己的结论是：如果真想长期用，优先放在开发机上，而不是本机。

    原因很简单：

    • 开发机更稳定
    • 可以长期在线
    • 更适合和 tmux 组合
    • 人离开电脑也不影响底层会话

    如果只是本机临时试一下当然也能跑，但一旦你要认真做“远程接管”，开发机基本更合适。

    2. 先把 tmux 理顺

    不要一上来就只盯 botmux。

    如果 tmux 没装好、默认终端不兼容、会话管理一团乱，后面飞书层再漂亮也只是把混乱远程暴露出来而已。

    所以我今天其实花了不少时间在这里，包括：

    • 装 tmux
    • 处理终端兼容
    • 让 devbox 上的终端体验先可用

    这一步打底之后，后面才有资格谈“飞书远程控制 Agent”。

    3. 选好底层 CLI

    Botmux 的好处是它不绑定单一 CLI。

    我这次接的是：

    • Claude Code
    • TraeX

    这就很舒服，因为你完全可以按自己的工作流来，不需要为了接飞书而换掉原来的工具。

    4. 飞书机器人最好按角色来建

    我这次是直接建了两个机器人，分别对应两个终端。

    这样做的好处是后面拉群时很自然：

    • 一个机器人就是一个 Agent 身份
    • 群里 @ 谁，基本就等于在叫哪个底层 CLI

    如果以后再扩展，比如加一个偏检索、偏 review、偏运维的 Agent，这种组织方式也比较顺。

    这里最值得注意的一点，是**工作目录不要图省事直接给 ~**。

    我更倾向于给项目父目录，或者一个明确的工作区目录。这样后面无论是扫描、路由还是会话落点都会更干净，也不容易把无关目录全卷进去。

    现在跑通之后，体验上最大的变化是什么

    最大的变化其实不是“我能在飞书里聊天了”，而是：

    远端开发机上的 Agent，终于变成了一个可以被随时接管的长期在线工作对象。

    这个差别很大。

    以前终端里的 Agent 更像“我坐在电脑前时才能调动的助手”。

    现在更像：

    • 它在开发机里持续活着
    • 飞书是它的远程入口
    • tmux 是它的底层生存层
    • botmux 是桥

    一旦这个感觉建立起来，很多之前只是“想想挺美”的工作流就真能落地：

    • 下楼路上看一眼任务跑得怎么样
    • 在手机上给远端 Agent 补一句指令
    • 直接拉群让两个 Agent 讨论
    • 后面做 oncall、值班分析或者定时播报

    这套方案适合什么人

    如果你符合下面几条，我觉得很值得试：

    • 已经长期在用某个 Agent CLI
    • 经常 SSH 到开发机干活
    • 习惯让终端会话常驻
    • 想从手机或飞书继续控制远端任务
    • 想让多个 Agent 在一个协作空间里一起工作

    如果只是本地单机偶尔玩玩 Agent，其实直接用原生 CLI 就够了，不一定非要上 botmux。

    我现在对 Botmux 的理解

    今天折腾完之后，我觉得它最有价值的地方，不是“飞书里多了个机器人”，而是把下面几件事真正合成了一套工作流：

    • tmux 的常驻能力
    • 开发机上的 CLI 运行时
    • 飞书的协作入口
    • 多 Agent 并行

    简单来说，它把“远端终端 + Agent + 飞书协作”这三件原本分开的事，拼成了一个完整方案。

    这也是为什么我最后会选它，而不是只找一个能收发消息的普通 Bot 工具。
